# 背屏首次触发偶发被桌面覆盖：诊断记录（2026-10-16）

## 已确认的原因

手机记录证明，部分“一闪消失”是官方背屏应用在重启后异步恢复息屏状态，把官方Home重新置前。ReMRSS内容已经启动，但失去前台，计时和进程仍在继续。

共用的 `TaskService.disableSubScreenLauncher()` 实际执行 `am force-stop com.xiaomi.subscreencenter`。充电、通知、磁贴/URI投放均调用它，投放保活服务还会额外杀一次官方进程。系统会重新启动官方SECONDARY_HOME；官方应用初始化后存在如下回调：

1. 延迟1000ms执行重启后的息屏恢复检查。
2. 读取Secure设置 `sub_screen_restart_nap_after_start`；当前手机值为1。
3. 调用带有 `SubScreenRestartDozeListener` 标记的 `wakeUp`，紧接着对display1调用 `goToSleep`。
4. 系统进入Doze并将官方Home置前；ReMRSS持续发WAKEUP时只能把屏幕再次点亮，不能保证原内容回到前台。

上述官方实现取自手机安装的 `com.xiaomi.subscreencenter` APK（RELEASE-1.0.2609141923 / 426091419），其UID为10209。`SubScreenCenterApp` 初始化调用与混淆类 `k2.J` 的Runnable分支对应，条件与系统日志吻合。1000ms是初始化完成后的调度延迟，并非从ReMRSS内容出现开始计时。

## 当前判断与边界

- 充电和通知已捕获“官方重启息屏→Home置前”的实际因果时间线；这是一个有实机证据的共同缺陷。
- App投放使用同一杀进程链路，并受到保活服务额外杀进程和前台检测的影响，存在相同风险；本轮没有捕获一次独立的投放失败全链路，不将三类所有失败一概认定为该原因。
- 间歇性符合初始化、息屏状态与前台切换之间的竞争。但用户提到的“第二次通常正常”仍需要失败/重试成对日志进一步确认，不能仅凭这次回调推断每次第二次触发为何恢复。
- 现有启动验证主要检查任务是否位于display1，不能证明在异步回调结束后仍在前台。模拟器也没有该小米官方进程及其重启息屏逻辑。

## 修复方向

先调整共用的背屏启动流程，避免靠反复杀整个官方包争夺前台；将屏幕唤醒完成与目标任务实际位于前台作为成功条件。对已确认的系统回调竞争做有限的状态复核/恢复，且恢复操作必须属于当前会话，避免旧充电/通知结束回调覆盖新任务。

同时需要核对投放保活服务：瞬时失焦不应立即判定用户关闭App，也不能由旧服务销毁时无条件启动Launcher覆盖新内容。后续验收应覆盖息屏后的首次触发、快速第二次触发以及三类功能互相打断。

## 诊断阶段操作与连接

本轮只读设备日志、系统设置和官方APK；未改变业务代码、手机息屏配置或电池模拟状态，未安装新包、提交或发布。完整日志包含少量无效UTF-8，保存原始字节并以replace解码分析。私有证据位于被忽略的 `.local/diagnostics/first-trigger-20261016/`，未加入Git。

用户要求拔掉USB后继续网络调试，已使用手机现有、已配对的无线ADB TLS连接，并通过该连接核对序列号/型号及上述设置值；没有额外开放传统5555端口。
